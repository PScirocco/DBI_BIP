## 変更6: 累積時間Mapの明暗反転　✅ 完了 2026-10-13

- [x] `_MapView._norm()` に切り出し、stat のみ `1-v`（deg は無変更）
- [x] `map.rangev` に注記追加: `正規化・反転表示: 暗＝累積大 (max {v})` / `normalized & inverted: dark = more accumulated (max {v})`
- [x] `test_ui.test_run_small_sequence_end_to_end` に反転の数値検証を追加
- 所見: サンプル動画では大半の画素が面内最大よりかなり小さいため、反転後はほぼ全面が明るくコントラストが低い（反転前は逆にほぼ全面が暗かった）。見づらければ正規化方法の見直しを別途相談

**対象**: `bisim/ui/tabs/results.py` の `_MapView.reload()`

現状（deg/stat 共通）:
```python
def norm(a):
    return np.clip(a / vmax, 0.0, 1.0)
```

変更（stat のみ反転。deg は現状維持＝「明=劣化少」のまま）:
```python
def norm(a):
    v = np.clip(a / vmax, 0.0, 1.0)
    return (1.0 - v) if self.kind == "stat" else v
```

- カーソル値・統計行（`lbl_stats`）は `raw[c]`（生の値）を見ているので無変更でよい。
- `map.rangev` のラベル文言「面内最大で正規化 (max {v})」に「暗=高ストレス」の注記を足すか検討
  （例: `正規化・反転表示 (暗=高ストレス, max {v})`）。i18n.py で ja/en 両方。

**影響範囲**: results.py の1関数 + i18n 1キー。`test_ui` の `view_stat.reload()` 呼び出しは
「例外が出ない」だけを見ているので既存テストは壊れない。可能なら
`_raw` の値から「norm後の配列が反転されているか」を数値で検証する軽いテストを追加するとよい
（例: stat 値が大きい画素ほど `1-v` が小さい＝暗いことを assert）。

**工数**: 30〜45分

## 変更7: Degraded previewのスクロールバーにAging時間表示　✅ 完了 2026-10-13

- [x] `RunResult.dt_accel` 追加（動画のみ非ゼロ）
- [x] `ResultEntry.seconds_per_frame` / `base_aging_seconds` 追加（通常完了・停止保存の2箇所）
- [x] `ResultsTab._frame_text()` で `Frame {v} (aging {aging}, cumulative)` 表示。言語切替時も再描画
- [x] `res.frame_aging` キー追加、`test_engine` / `test_ui` にテスト追加
- 注意: `base_aging_seconds` の「累積」は **1回の実行（Run）内** の前ステップ分のみ（`run_sequence` の `cumulative` と同じ＝④タブの Aging 時間表示と同じ基準）。
  ステップを単独実行／停止位置から再開した場合、それ以前に別実行したステップの時間は含まれない
- 注意: フレーム v の表示は方針どおり `base + v×dt_accel`（フレーム開始時点）。最終フレームは④タブの合計より 1 フレーム分小さい

**キモ**: 1フレームあたりの加速込み時間（`dt×ACCEL_RATIO`）と前ステップまでの累積時間は
**`bisim/engine.py::run_recipe` に既に計算済み**（AGING_TIME周回対応のため、`dt_accel` という
ローカル変数がある。行番号はコード参照）。これを `RunResult` → `ResultEntry` まで引き回すだけでよい。

### 手順

1. **`bisim/engine.py`** — `RunResult` に `dt_accel: float = 0.0` フィールドを追加し、
   `run_recipe()` の戻り値構築時に（動画のときのみ非ゼロで）セットする。
   静止画は `dt_accel=0`（PQ評価は寄与ゼロのまま）。

2. **`bisim/ui/main_window.py`** — `ResultEntry` に以下を追加:
   ```python
   seconds_per_frame: float = 0.0
   base_aging_seconds: float = 0.0   # このレシピ開始時点での累積Aging時間
   ```
   `_step_done`（通常完了）と `_handle_stopped`（停止保存）の両方で `ResultEntry` 生成時に:
   ```python
   base_aging_seconds=res.cumulative_aging_seconds - res.aging_seconds,
   seconds_per_frame=res.dt_accel,
   ```
   を渡す（`res` = `RunResult`）。

3. **`bisim/ui/tabs/results.py`** — `ResultsTab._show_frame(v)` で、動画のときフレーム番号 v から
   Aging時間を算出し表示に加える:
   ```python
   entry = self.main.current_result()
   if entry and entry.seconds_per_frame > 0:
       t_sec = entry.base_aging_seconds + v * entry.seconds_per_frame
       self.lbl_frame.setText(t("res.frame_aging", v=v, aging=engine.format_aging(t_sec)))
   else:
       self.lbl_frame.setText(t("res.frame", v=v))
   ```
   （`engine.format_aging` は既存の時間フォーマッタを再利用。`results.py` 先頭で
   `from bisim import engine` を import）

4. **`bisim/ui/i18n.py`** — 新キー:
   ```python
   "res.frame_aging": {"ja": "フレーム {v}（Aging {aging}、累積込み）",
                        "en": "Frame {v} (aging {aging}, cumulative)"},
   ```

### 注意点
- `dt_accel` は AGING_TIME 周回時も1フレームあたり一定（`dt × ACCEL_RATIO`）なので、周回をまたいでも
  単純な線形計算で正しい。
- `frames_done == 0` のケース（停止直後など）で `seconds_per_frame` 計算に使う分母は無いので問題なし
  （上記は `dt_accel` を直接使うのでゼロ除算は発生しない）。
- 静止画（PQ評価）はスライダ自体が無効なので対象外、現状の `run.dash` 表示のままでよい。

**影響範囲**: engine.py（RunResult 1フィールド）/ main_window.py（ResultEntry 2フィールド、
生成箇所2箇所）/ results.py（表示ロジック）/ i18n.py（1キー）。
`test_engine.py` の `RunResult` を直接構築しているテストがあれば dataclass フィールド追加で
壊れないか確認（キーワード引数で渡している前提なら影響なし）。`test_ui.py` に
「フレーム送り→表示文字列にAging時間が出る」ことを確認する軽いテストを追加すること。

**工数**: 1.5〜2.5時間（データの受け渡し＋表示整形＋テスト込み）
